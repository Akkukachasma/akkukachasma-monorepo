# Debugging

- Accepts and rewards a layered diagnosis instead of a shallow one: symptom (500 on an endpoint) → dev-log grep for the real error → reproduce the exact failing query in isolation → query the DB directly to name the offending rows. Keep narrowing until a specific root cause is identified. Confidence: 0.6
- Values exactness when diagnosing: distinguish "simple query works" from "the specific filtered query with includes fails", and report concrete counts and record IDs (e.g. "9 of 10 docs missing `aspect_ratio`") rather than a vague "data looks wrong". Confidence: 0.6
- Re-tests suspected failures empirically before reporting them: re-curl the "timing out" endpoints and fire parallel requests mirroring the page's concurrent fetches, to show they return fast and prove the symptom was a cold-start artifact rather than a real bug. Confidence: 0.6
- Expects the agent to own and retract its own wrong conclusions mid-diagnosis ("I tested the wrong path — the code is correct") rather than quietly letting a false lead stand. Confidence: 0.6
- Bracketed Next.js route folders (`app/[product_slug]/`) break the read_file/glob tools — fall back to `sed -n '1,40p' 'app/(with_mobile_nav)/[product_slug]/page.tsx'` via shell, quoting the path. Confidence: 0.6
- Only stops dev servers it started itself; when the user has already launched the stack in their own terminal, leave those processes alive and diagnose against the live ports instead. Confidence: 0.6
- For scratch/repro scripts, writes them into the session scratchpad and copies them into the target workspace to resolve modules, then deletes them — keeps repro artifacts out of the repo. Confidence: 0.5
- Before reporting a piece of infrastructure as absent, check the running system, not just the codebase: the user caught a "Redis not installed" claim by noting Redis is a server concern they deploy later — verify with an actual probe (`lsof -iTCP:6379`, `redis-cli ping`) and separate "npm package/code absent" from "service not running". Confidence: 0.55
- Treats *absences* as first-class findings when auditing a stack: explicitly report what is missing (no cache layer, no index on `is_featured`, no pool size set, `force-dynamic` making `revalidate` dead code) alongside what exists — missing pieces are usually the actual bottleneck. Confidence: 0.55
- When a connection to a host fails, escalate the diagnostic layer by layer instead of stopping at the first error and bouncing it back: SSH on the default port → scan the plausible alternate ports → ICMP reachability (ping/traceroute) to separate "host down" from "port filtered" from "auth rejected". Report each layer's result in one line and keep working the problem yourself. Confidence: 0.6
- For open-ended architecture audits, prefers delegating parallel structured investigations (backend, frontend) with an explicit checklist and a "concrete evidence with file paths and line numbers" requirement, then synthesizing into one ranked answer — rather than a surface-level summary. Confidence: 0.5
- When an auth wrapper silently fails, **instrument the wrapper instead of blindly re-trying variants**: first prove the env var actually reaches the child (a `probe.sh` printing `${#VAR}` rules out a scope/export bug), then prove the askpass hook is even being invoked (have the helper append a line to a log file and read it back — an empty log means the hook never fired, so the ssh flags are wrong, not the password). Each step eliminates one layer, and the log-instrumentation trick makes an invisible invocation visible. Confidence: 0.5
- For a browser-reported CORS / blocked-request error, reproduce it server-side before reading any code: `curl -i -H 'Origin: <failing origin>'` on the exact failing URL, then a **control test** with a known-allowed origin, then an `OPTIONS` preflight — the difference proves it's the allowlist and not the endpoint. Then trace the rejected origin back to the exact env/config line that governs it (e.g. an `ALLOWED_ORIGINS` value that omits the port, so `http://<ip>` is allowed but `http://<ip>:3000` is not). Confidence: 0.55
- To clear a third-party/browser-extension error (chrome-extension `injected.js` + `web_accessible_resources` warning, ad-blocked `ERR_BLOCKED_BY_CLIENT` telemetry), *prove* it isn't yours before dismissing it instead of asserting: `grep -rl <domain>` the deployed frontend dir, `grep -rn <domain>\|sub_filter` the nginx conf (catches server-side script injection), then `curl` the live page and grep the HTML — zero hits everywhere plus a 200 homepage settles it. Close with a one-step self-check the user can run in their own browser (open the URL in an incognito/private window) so they can confirm the noise disappears without you seeing it. Confidence: 0.5
- Verifies a deploy fix by counting rendered data keywords in the HTML (e.g. `featured`/`categories`/`products` going from 0 to real counts) and matching it to the production API-URL line in the server logs — proves SSR now hits the right backend, beyond just a 200 returning. Confidence: 0.6
- Treats "same code, different result on another server" as the key clue and hands it over as a *contrast*, not a question ("maine ye same code ek aur server pe deploy ki, wahan frontend alag aa rha hai, isme alag hai — main samajh nahi paa raha issue kahan hai"). The right move is a two-host deployment diff, not more code reading: inventory both deployed frontends side by side (dir listing, every `.env*` file dumped in full, `next.config` env/baseUrl/proxy references, nginx conf, node_modules/build state) and report the exact line where the two diverge. Include **how each host actually runs the process**, not just the files: probe both PM2 and Docker on each box (`pm2 list` / `pm2 env <id>` / `pm2 describe` for script+cwd+env, `docker ps` for image/ports) and diff the orchestration — container env vs host `.env`, nginx `proxy_pass` upstream, deployed image tag vs `.next/BUILD_ID` and whether `node_modules` is installed on the box. The user volunteers the other host's stack ("par woh docker se deploy hai") and that fact redirects *where* the config to compare lives. Confidence: 0.6
- When a Next.js frontend "behaves differently on another host", the runtime env can be a dead end — `NEXT_PUBLIC_*` is inlined at build time, so an empty `docker exec <frontend> env` proves nothing. Go read the value **out of the build artifact**: `docker exec <c> sh -c "grep -rhoE 'https?://[^\" ]+' .next | sort | uniq -c | sort -rn"`, and grep for the API path prefix (`(/v1|/api)/[a-z-]+`) to see which routes are baked in. Do the same on both hosts and diff the baked hosts/prefixes (e.g. `https://qa-api.<domain>` + `/v1` vs `http://<ip>` + `/api`) — that divergence is the root cause, and no amount of PM2 env editing or nginx tweaking can change it without a rebuild. Confidence: 0.55
- When auditing a Docker-based reference host, prefer the **source-of-truth config** over what the container ships: the image's `/etc/nginx/conf.d/*.conf` is often the stock default while the real routing lives in the bind-mounted `docker-compose.yml` / custom `nginx.conf` under the infra dir (`find / -maxdepth 4 -name 'docker-compose*.y*ml'`, then read the mounted conf). Reading the container default first sends you chasing a config that isn't in effect. Confidence: 0.5
- When he opens with his own theory ("yaar issue pata hai kya hai…"), treat it as a hypothesis to be tested against evidence, not the request itself — confirm or refute it explicitly, then keep narrowing on the actual divergence instead of stopping at the restatement. A short mid-diagnosis sentence ("par woh docker se deploy hai", "wo port 3001 pe hai") is a **constraint correction**, not a new task: fold it into the current investigation and re-check what you assumed, don't restart or re-plan the whole thing. Confidence: 0.5
- To close out a live prod fix, re-issue **every** request that appeared in the browser console dump with the failing `Origin` header in a loop and assert the CORS header is present (print an explicit `NO ACAO` when absent), covering the preflight/OPTIONS case too — not just the one endpoint that was diagnosed. Then triage what still fails by cause: a 401 without a session is expected, a 404 is a data/route issue, neither is the CORS bug just fixed. State that separation explicitly so the user doesn't chase a resolved error. Confidence: 0.6
- When the user hands over a second host *and labels its role* ("ye uss server ki detail hai jo bilkul proper hai, shi chal rha hai — ab ye wala check kro"), that host is a **golden reference**, not just another data point: inventory its complete runtime first (process manager, build artifact / `BUILD_ID`, env files, listening ports, proxy/orchestration config), then diff the broken host line-by-line against that snapshot and report divergences as "reference has X, broken host lacks/changes X". Enumerate the reference before touching the broken host, so the comparison baseline is complete even if the second host turns out to be unreachable. Confidence: 0.5
- His answers to diagnostic questions are minimal and sometimes come back as the question itself pasted verbatim ("haa different dikh rha hai <your question>") — so a multi-part ask ("layout, ya data missing, ya images?") gets no more information than a yes. When the difference is a *visual* one between two builds, gather the evidence yourself: `curl` both rendered homepages and diff the HTML/markup, compare `.next/BUILD_ID` and the baked assets between hosts — don't wait on a browser description he isn't going to give. When the reference host is reachable, the decisive version of this is to hit the **same API endpoint** on the working host and locally and compare payload size plus extracted record codes (byte-identical responses — same byte count, same 11 product codes — eliminate DB and code as causes) and then pivot to cache / branch / missing assets instead of re-litigating env. Confidence: 0.5
- "Is the server's env different from ours?" is a recurring ask (hands over `username / IP / password` inline, names the working QA host, asks specifically about the backend env) — answer it as a **two-stage diff**, never an env dump. Stage 1, key sets: `grep -oE "^[A-Z0-9_]+" <file> | sort -u > x.keys` then `comm -23 srv.keys ours.keys` (missing here), `comm -13` (extra here), `comm -12 | wc -l`. Stage 2, values: a `mask()` function that scrubs `mongodb+srv://user:pass@`, `SECRET_KEY`, AWS keys, SMTP password, Google client id/secret and Razorpay keys before printing either file; verify critical secrets without exposing them (`a=$(grep "^SECRET_KEY" …); [ "$a" = "$b" ] && echo "MATCH (len ${#a})" || echo DIFFERENT`); reduce `DATABASE_URL` to `host / db`. Close with a table where each difference is classified — intentional infrastructure (`PORT`, `REDIS_HOST`, `FRONTEND_URL`), genuinely missing (`CACHE_ENABLED`/`CACHE_REDIS_ENABLED`), or real divergence (`SMTP_EMAIL`, `MANIFEST_ORDER_API`) — and every row answers "UI pe asar? ❌/✅" so the diff lands on a verdict. Confidence: 0.6
- Before recommending "set this env var", prove the code actually *reads* it — a hardcoded `if (process.env.NODE_ENV !== "development") return "https://qa-api.<domain>"` in `lib/api.ts` makes `NEXT_PUBLIC_API_URL` a no-op, and the proof is that the string `NEXT_PUBLIC_API_URL` appears **zero** times in `.next` while the qa host is baked in, plus the Dockerfile setting no `ENV` for it. Corollaries: grep the Dockerfile alongside the runtime build (build args and `ENV` lines are what decide the baked value), and quote the offending code block back to the user — "setting the var changes nothing, the code never reads it" — since that's the finding that redirects the whole task. Confidence: 0.6
- Before blaming an env var for a symptom, read the code that consumes it (`grep -rn <VAR>` and the surrounding function) to prove the link — `DEV_ENVIRONMENT=true` looks alarming in a diff but only selects the upload folder for *new* images, not product assets, so it cannot cause a visual diff; say so and drop it instead of speculating. Corollary: when the diff is real but symptom-neutral, state plainly "env aur database problem nahi hain", list the 3 remaining candidate causes concretely (hard refresh/incognito, missing CSS/fonts/images, a stale checkout on another branch serving that port), and hand back the one command to run — don't re-open the env investigation. Confidence: 0.55
- Automation scaffolding can outlive its usefulness: an `expect` script, an `sshpass` availability check, and then an `SSH_ASKPASS`+`SSH_ASKPASS_REQUIRE=force` helper is three failed layers of indirection to do what one human keystroke does. Each extra layer costs the user a "what is this?" interruption they have to pay for in comprehension. Before building the next wrapper, ask whether the user can just run the one command and paste the output — and never present the *choice* of tools (`sshpass` vs `expect` vs askpass) to him; that is your problem to solve, silently. Confidence: 0.5
- When a locally-built app renders visibly differently from a known-good deploy, suspect the **git branch** before the code: the working copy sits on the default branch (`main`, July 26) while the good host runs a release branch (`origin/qa`, Sep 6). Enumerate every remote branch — `git fetch origin` then `git log -1 origin/<branch> --format="%h %ad %s" --date=iso` for main/qa/prod — and match their commit dates against the deployed artifact's own timestamp (`docker inspect <c> --format "{{.Created}}"`, `.next/BUILD_ID`, `stat` on the build dir). The branch whose date equals the live build date is the code actually serving traffic; that is the root cause of the visual drift, and it needs a content swap, not a config or env fix. Confidence: 0.6
- A remote-branch commit date that matches the live build timestamp tells you *what the live host is running*, not *what your local checkout contains*: the two trees can differ by only ~25 frontend / ~13 backend files (two versions of one codebase, not old-vs-new), and the "signature feature" used to prove staleness (e.g. a `price-adjustment` module) may already exist in **both** the branch and the workspace app. Before declaring one copy stale, take the full `diff -rq` file-name list (`| sed 's|.*/qa/frontend/||; s| and .*||'`) and re-probe the marker in all three locations — remote branch, workspace app, and the running container — then state the provenance only as far as the evidence actually reaches. Confidence: 0.55
- A "this feature only exists in the newer branch" probe is a **weak discriminator and often silently wrong**: the same marker (e.g. a `price-adjustment` / `bulk pricing` module) turned out to exist in the `qa` branch, in the `main` branch, and in both the qa and prod containers, so it proved nothing. Prove branch↔deploy identity by **correlating timestamps across all candidates at once** — dump the image tag + `docker inspect <c> --format "{{.Config.Image}} | created={{.Created}}"` for every container, then `git log -1 origin/<b> --format="%H | %ad | %cd" --date=iso` for every branch — and let the matching build-time/commit-time pair carry the conclusion. Corollary: when a container's build timestamp matches **no** branch head (e.g. an Oct 1 image on a repo whose heads are Jul 26 and Sep 6), say so explicitly — it is a manual/ad-hoc deploy that no branch explains, not a third "branch". When an earlier proof attempt collapses, retract both attempts in a numbered list rather than quietly presenting the surviving one. Confidence: 0.55
- Two copies of the same app cannot be compared by file counts or directory shape — identical `find | wc -l` totals across `app/`, `features/`, `components/` coexisted with real content drift. Establish parity with `diff -rq --exclude=node_modules --exclude=.next --exclude=dist --exclude=.git <a> <b>`, then `md5 -q` the individual files that looked different to confirm or refute the suspected divergence before acting on it. Confidence: 0.55
- When bringing a swapped-in stack up locally and a port is already taken by a process the user started (their own standalone dev server), do **not** kill it or fight over the port — identify the owner with `ps -p <pid> -o command` / `lsof -a -p <pid> -d cwd`, confirm it isn't yours, then start the new app on a free adjacent port (e.g. 3001). The same attribution rule applies *after* a teardown: stopping your own background task IDs often leaves a child process still holding the port, so attribute that residual PID (owner + cwd) before touching it — never blanket-kill. And a busy port is not automatically a dev server: enumerate *every* PID on it with its cwd first, because a browser (e.g. Brave holding :3000) can appear as a listener and must be left alone — kill only the `node`/`next-server` PIDs and name the ones you skipped. When the new app does take a different port, **add that exact origin to the backend's CORS allowlist** (`ALLOWED_ORIGINS`) so the moved origin stays reachable. Verify the CORS header for the *new* port specifically, and tell the user which port the new build is on. Confidence: 0.6
- A branch↔deploy probe only works once the marker is **proven exclusive** to one branch, so find it by diffing the candidates first (`git diff origin/main origin/qa -- frontend/app/layout.tsx` surfaces the genuinely distinguishing artifact — here the `DM Sans` font added in `qa`), then grep each live site's HTML for it and cross-check with a branch-exclusive string such as a QA-only analytics ID (`G-8ELTC6BRCE`) that appears on one site and is absent on the other. That pair settles branch identity for a purely visual complaint. Symmetry matters: fetch *both* candidate environments in one pass (curl the production apex and the qa subdomain, record size + extracted content counts for each) rather than comparing local against only one host — otherwise the env you never fetched is the one hiding the answer. Confidence: 0.55
- Treat "run it locally and check CORS / resolve any CORS issue" as the **acceptance gate for a code swap**, to be cleared *before* any deploy: the local boot → poll the backend port until it answers → `curl -H "Origin: http://localhost:<newport>"` for `Access-Control-Allow-Origin` (plus an `OPTIONS` preflight) across several endpoints → confirm the frontend page actually renders real data pulled from that backend (grep product codes / image URLs in the returned HTML) before declaring the swap good. Confidence: 0.6
- A MongoDB Atlas "Server selection timeout: No available servers / ReplicaSetNoPrimary + received fatal alert: InternalError (alert 80)" does **not** mean the connection-string is wrong — the server replying at all (TLS handshake alert) proves the host+creds are valid, and alert 80 on handshake is Atlas's **Network Access IP allowlist** rejecting this machine's public IP. When the user hypothesizes the URL is bad ("DB ka url hi nahi hai?"), test it before agreeing: check no shell-exported `DATABASE_URL` is overriding `.env`, then probe the exact `.env` value with a throwaway Node/mongodb script (resolve the package straight off `.pnpm` since it won't resolve in the scratchpad dir) that redacts creds on print, times the failure, and prints the error code — then report "URL galat nahi hai, IP allowlist hai" with the precise fix (add current IP / `0.0.0.0/0` in Atlas → Network Access). Confidence: 0.5
